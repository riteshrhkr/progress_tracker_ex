== Warm-up

*1. What is the difference between a class, an object and a reference?*

A class is the description of fields and methods. An object is a block of heap memory holding one set of those field values. A reference is the address of that object, and it is the only thing a variable ever holds. Two references can point at one object, which is why `==` asks "same object" rather than "same contents". link:oop-fundamentals.adoc[Details.]

*2. Is Java pass-by-value or pass-by-reference?*

Always pass-by-value. For a reference type the value copied is the address, so the method can mutate the object you passed but cannot make your variable point elsewhere.

*3. Can you override a `static` method?*

No. You can declare one with the same signature in a subclass, which *hides* it. The compiler picks based on the declared type, and `@Override` on it is a compile error: `static method statik() in Sub cannot be annotated with @Override`.

*4. What does a subclass inherit?*

Every non-private field and method, subject to access rules. Not constructors, not initializer blocks. `private` members exist in the object but the subclass cannot name them.

*5. What are the default values of fields?*

`0` for integral types, `0.0` for floating point, `false` for `boolean`, `'\u0000'` for `char`, `null` for references. Local variables get no default and the compiler refuses to read them: `variable x might not have been initialized`.

*6. Interface or abstract class — one thing each can do that the other cannot?*

An abstract class can hold instance state and have a constructor. An interface can be implemented many times by one class. Full comparison in link:four-pillars.adoc[four-pillars.adoc].

*7. What does `final` mean on a field?*

The variable can be assigned exactly once and never repointed. It says nothing about the object it points at — a `final List` can still be added to.

== Practical

*8. You added a class to a `HashSet` twice and the size is 2, though the two objects are equal. What happened?*

`equals` is overridden and `hashCode` is not, so the two objects land in different buckets and are never compared. Nothing throws. `javac -Xlint:all` reports it: `Class BadUser overrides equals, but neither it nor any superclass overrides hashCode`. Demo: link:examples/contracts/EqualsHashCodeDemo.java[EqualsHashCodeDemo.java].

*9. A `final` field is `null` inside one of your methods. How is that possible?*

The method is overridable and was called from a superclass constructor. Subclass field initializers run after the superclass constructor finishes, so the override ran while the fields were still at their defaults. Output showing it: link:examples/basics/ConstructorOrderDemo.java[ConstructorOrderDemo.java].

*10. Your class has a `private final List` and callers keep corrupting it. Why?*

The getter returns the field itself. `private` protects the reference, not the object. Return `List.copyOf(...)`, or store an unmodifiable collection internally. Note the difference: `List.copyOf` is a snapshot, `Collections.unmodifiableList` is a live view that reflects later changes to the source.

*11. When would you use a `record` instead of a class?*

When the type is genuinely its components and nothing more, and you want `equals`, `hashCode`, `toString` and accessors generated consistently. Not when you need to hide part of the representation, subclass it, or evolve the API separately from the fields — records are `final` with public accessors.

*12. How do you make a class immutable?*

Class `final` (or private constructors), all fields `private final`, no state-changing methods, copy mutable objects on the way in and on the way out. Records need a compact constructor for step four; they are only shallowly immutable.

*13. You need to add a method to a widely implemented interface without breaking anyone. Options?*

Give it a `default` body — that is why default methods were added in Java 8. If it cannot have a sensible default, add a new sub-interface, or accept the breaking change and coordinate it. Adding an abstract method to a published interface is a source and binary compatibility break for implementors.

== Senior

=== 14. Why prefer composition over inheritance?

*The line of thinking:* the question is what you become coupled to. Extending a class couples you to its fields, its implementations, and to which of its own methods it calls internally — and that last one is not in the Javadoc.

*A good answer:* subclassing depends on the parent's *self-use*, which is undocumented and can change between versions. Extending `HashSet` to count additions gives 6 for three elements, because `AbstractCollection.addAll` calls `add` in a loop and the override counts both. A wrapper holding a `Set` field counts 3, exposes only the methods you choose, and can swap the implementation. Inheritance is still right for substitutable specialisation and template methods. Demo: link:examples/design/CompositionDemo.java[CompositionDemo.java].

*Likely follow-up: so when do you use inheritance?* When the parent was designed and documented for it or you own both sides, the relationship is genuinely substitutable, and the subclass weakens no promise. Template methods, `AbstractList`, `HttpServlet`, JUnit base classes.

=== 15. Explain the equals/hashCode contract and what actually breaks.

*The line of thinking:* start with the mechanism, not the five properties. Hash containers locate by bucket first and compare second.

*A good answer:* equal objects must have equal hash codes; unequal objects may collide. If `hashCode` disagrees with `equals`, an object is filed in one bucket and searched for in another, so the container silently misplaces it — no exception, just wrong answers. `equals` must also be reflexive, symmetric, transitive, consistent and false for `null`. Both must be built from fields that cannot change while the object is a key: mutate a key after `put` and the entry stays visible in `toString` while `get` returns `null`.

*Likely follow-up: `getClass()` or `instanceof`?* A real trade-off. `getClass()` guarantees symmetry and transitivity but means a subclass adding no fields is never equal to its parent, which breaks substitutability. `instanceof` preserves substitutability but breaks symmetry as soon as a subclass adds a field to the comparison — `p.equals(cp)` true, `cp.equals(p)` false. The practical resolution is to make value types `final` or records and use `instanceof`.

=== 16. Give a Liskov violation from real code and say what the real cause was.

*The line of thinking:* the classic example is `Square extends Rectangle`, but the interesting part is *why* it fails.

*A good answer:* code written against `Rectangle` sets width 5 and height 4 and expects area 20. A `Square` gives 16, because it cannot keep the promise that setting width leaves height alone. The cause is not geometry — it is mutability. Immutable `Rectangle` and `Square` value types substitute perfectly. The violation appeared the moment there was a setter whose contract a subtype could not honour. Demo: link:examples/design/SolidDemo.java[SolidDemo.java].

*Likely follow-up: how do you check for it?* A subtype must not strengthen what the caller has to provide, must not weaken what it returns, must not throw exception types the caller cannot expect, and must keep the parent's invariants.

=== 17. When is a `sealed` hierarchy better than plain polymorphism?

*The line of thinking:* they optimise for opposite kinds of change. Ask which axis is going to grow.

*A good answer:* polymorphism is right when new *implementations* keep arriving and the operations are stable — adding a shape must not touch the code that measures shapes. `sealed` is right when the *types* are fixed and the *operations* keep arriving, and you own the domain. With a sealed interface the compiler proves a switch is exhaustive, so adding a fourth payment type turns every incomplete switch into `error: the switch expression does not cover all possible input values` instead of a production surprise. Sealed is wrong for plugin points, because external code cannot extend it.

*Likely follow-up: what does `sealed` require?* Permitted subtypes must be named in `permits` (or inferable from the same file) and must each be `final`, `sealed`, or explicitly `non-sealed`. Java 17.

=== 18. An inner class caused a memory leak. Explain the mechanism.

*The line of thinking:* the reference is invisible in the source, so name it explicitly.

*A good answer:* a non-static inner class instance holds a reference to its enclosing instance — you can prove it by returning `Outer.this`. If anything long-lived keeps one small inner object, say a listener registered on a static bus or an entry in a cache, the entire outer object stays reachable and cannot be collected. The heap grows slowly and nothing in the code looks retained. The fix is `static` on the nested class, passing in only what it needs. The same reference is why serializing an inner object drags the outer along. Demo: link:examples/design/NestedClassDemo.java[NestedClassDemo.java].

*Likely follow-up: does a lambda have the same problem?* Only when it captures `this`. A lambda that captures nothing, or only local variables, does not retain the enclosing instance — but one referring to an instance field does, because that read goes through `this`.

=== 19. How would you design a `Money` type?

*The line of thinking:* it is a value, so the checklist is invariants, equality, immutability, and what must never be representable.

*A good answer:* store a `long` of minor units (or `BigDecimal`) plus a `Currency` — never `double`, because `0.1 + 0.2` prints `0.30000000000000004`. Make it immutable and `final`, with `equals`/`hashCode` over both fields so it is a safe map key. Arithmetic returns new instances and rejects mixed currencies by throwing, since silently converting would hide a bug. A `record` fits well, with validation in the compact constructor. Rounding mode belongs in the API of any operation that can produce a fraction, not in a default.

*Likely follow-up: why not `double`?* Binary floating point cannot represent most decimal fractions exactly, so errors accumulate across a ledger and totals stop reconciling.

=== 20. How do you decide what to make public?

*The line of thinking:* every public member is a versioned promise, so the cost is paid later, not now.

*A good answer:* start `private` and widen only under pressure. `final` by default on classes, because reopening a `final` class later is a compatible change while sealing an open one is not. Prefer exposing interfaces over concrete types on your API surface. Watch for the accidental leaks: a public field, a getter returning a mutable internal object, a `protected` method that exposes an implementation detail to subclasses forever.

== Trick questions

*21. Both a superclass and an interface provide the same method. Which wins?*

The class. "A class always beats an interface." A conflict between two *interface* defaults is different — that does not compile until you override and pick with `Walker.super.move()`.

*22. Can a constructor be `final`, `static`, `abstract` or `synchronized`?*

None of them. Constructors are not inherited, so `final` and `abstract` are meaningless; they are inherently tied to an instance, so `static` is contradictory; and the object is not yet published, so `synchronized` is pointless. `private` is allowed and useful for static factories and singletons.

*23. Can you overload a method by changing only the return type?*

No. Overload resolution uses the parameter list only. Same name, same parameters, different return type is a compile error. Overriding may narrow the return type — that is covariant return, and it is a different rule.

*24. Is `private` truly private?*

At the language level, yes. At runtime, reflection can read it unless a security manager or module encapsulation stops it, and a nested class can access the private members of its enclosing class. `private` prevents accidents, not determined access.

*25. Can an interface have a `private` method?*

Yes, since Java 9, as a helper shared by `default` methods. It is not part of the interface's API.

*26. Does `finally` run if `try` returns?*

Yes, before the value is returned. If `finally` also returns, it wins and discards the `try` result — which is why returning from `finally` is a bug rather than a feature.

*27. Two objects with the same `hashCode`. Are they equal?*

Not necessarily. The contract only runs one way: equal objects must share a hash code. Unequal objects sharing one is a collision, which is legal and expected.

== Predict the output

*28.*

[source,java]
----
class A { String name = "A"; String who() { return "A"; } }
class B extends A { String name = "B"; String who() { return "B"; } }

A ref = new B();
System.out.println(ref.name + ref.who());
----

Answer: `AB`. The field comes from the declared type, the method from the object. link:four-pillars.adoc[Why.]

*29.*

[source,java]
----
static String pick(Object o) { return "Object"; }
static String pick(String s) { return "String"; }

Object o = "hello";
System.out.println(pick(o) + pick("hello"));
----

Answer: `ObjectString`. Overloads are resolved at compile time from the declared type.

*30.*

[source,java]
----
static String f(long l)    { return "long"; }
static String f(Integer i) { return "Integer"; }
static String f(int... i)  { return "varargs"; }

System.out.println(f(7));
----

Answer: `long`. Widening is tried before boxing, and boxing before varargs.

*31.*

[source,java]
----
Integer a = 127, b = 127, c = 128, d = 128;
System.out.println((a == b) + " " + (c == d));
----

Answer: `true false`. The `Integer` cache covers -128 to 127.

*32.*

[source,java]
----
class Base {
    Base() { init(); }
    void init() { System.out.println("Base.init"); }
}
class Derived extends Base {
    private String value = "set";
    @Override void init() { System.out.println("Derived.init value=" + value); }
}
new Derived();
----

Answer: `Derived.init value=null`. The override runs before the subclass field initializer.

*33.*

[source,java]
----
Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
System.out.println(set.contains(new Point(1, 2)));
----

Answer: it depends entirely on whether `Point` overrides `hashCode`. With `equals` alone it prints `false`; with both it prints `true`.

== Rapid fire

[cols="2,3"]
|===
|Question |Answer

|Multiple inheritance of classes in Java?
|No. Of interfaces, yes.

|Can an abstract class have no abstract methods?
|Yes. It just cannot be instantiated.

|Can an interface extend multiple interfaces?
|Yes.

|Can you instantiate an interface?
|No, but an anonymous class or a lambda can implement one inline.

|Can an override throw a broader checked exception?
|No. Same, narrower, or none. Unchecked exceptions are unrestricted.

|Can an override reduce visibility?
|No. `attempting to assign weaker access privileges`.

|Does overloading care about the return type?
|No, only the parameter list.

|Is `Object.equals` reflexive by default?
|Yes; it is `this == obj`.

|What is `Objects.hash` doing that costs something?
|Allocating a varargs array on every call.

|Can a `record` extend a class?
|No. It is `final` and already extends `java.lang.Record`. It can implement interfaces.

|Can a `record` have static fields?
|Yes. Non-static instance fields beyond the components are not allowed.

|Are nested records static?
|Yes, implicitly.

|Can an inner class declare static members?
|Yes, since Java 16.

|What is `Outer.this`?
|The enclosing instance held by an inner class.

|Marker interface?
|One with no methods, used as a type-level flag, such as `Serializable`.

|Is `clone()` recommended?
|No. Prefer a copy constructor or static factory; `Object.clone` is shallow and awkward.
|===

== Mock round

Ten tasks, roughly 45 minutes. Do them without looking at the other documents, then check yourself against them.

. Design an immutable `Money` type with currency-safe arithmetic. State every invariant before you write a line.
. Write `equals` and `hashCode` for a `User` with `id`, `email` and `lastLogin`. Justify which fields you used.
. You must add per-operation metrics to a `Map` implementation you do not own. Do it without inheritance and explain the choice.
. Given a `PaymentProcessor` that calls `System.currentTimeMillis()` and `new SmtpClient()` directly, refactor it to be testable and write one test.
. Explain, with the sequence of steps, how a `final` field can be observed as `null`.
. Model shapes for a rendering engine where third parties add shapes, then model payment methods for a system where you own every type. Justify the different structures.
. Take a `Store` interface with `read`, `write`, `delete` and `bulkImport` where two of four implementations throw `UnsupportedOperationException`. Fix the design.
. Explain what happens when a `HashMap` key is mutated after insertion, at the level of buckets and hashes.
. A service holds a listener registered on a static event bus and the heap grows over days. Give the mechanism and the fix.
. Choose between `record`, `final class` and an open class for: a DTO from an HTTP response, a JPA entity, and a domain type with validation rules. Defend each.
